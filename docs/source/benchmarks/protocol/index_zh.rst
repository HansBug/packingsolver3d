协议与注意事项
==============

本页准确说明 :doc:`../leaderboards/index_zh` 里的数字是怎么得到的，读者据此判断能信到什么程度，也能照着重新生成。

预算与机器
----------

* **packingsolver3d** 通过 :func:`packingsolver3d.box.solve` 调用，``time_limit=10.0``\ 、``memory_limit=1024``\ ，其余选项默认（anytime 模式，上游所有子算法启用）。上游 ``box`` 在背包实例上会用到多个线程；没有做任何绑核处理。
* **第三方库** 在接受时间预算的情况下（U-Nesting 的元启发式）使用同样的 10 s；贪心类库远不到一秒就结束，没有重复运行。
* **参照程序** 按各自的预算运行：CP-SAT 模型 20 s、单线程、4 GiB；Martello-Pisinger-Vigo 程序 1 s、单线程。它们在表中标为"参照"，用来认证最优值，不参与竞争。
* 每个 case 只跑一次。上游的 anytime 模式无法精确到节点复现，未被证明最优的 case 重跑可能有出入。
* 机器：Intel Core i7-11700，16 个硬件线程，Linux 6.8，CPython 3.10；packingsolver3d 从 ``packingsolver3d.config.meta`` 里固定的上游 commit 构建。

每个解都被重新校验
------------------

不采用任何参与者自报的目标值。所有解，包括我们自己的，都以摆放（物品类型、箱子、位置、尺寸）形式存储，``tools/make_benchmarks.py`` 以百万分之一的容差检查下列各项后，才从摆放和实例文件重算目标值：

* 每个盒子都在其箱子内部，
* 同一箱内任意两个盒子不重叠，
* 任何物品类型的摆放次数不超过其份数，
* 每个盒子的尺寸是其物品类型的某个旋转，在固定姿态变体下必须是\ **精确**\ 的那个朝向，
* 目标为最小化箱数时所有物品都已装入。

任何一项不通过的解显示为 ``invalid``\ ，该参与者在该基准的总计变为 ``n/a`` 并附合法 case 数。U-Nesting 的四个元启发式就是这样失去 THPACK9 总计的：在 47 个实例中的七到九个上它们的摆放伸出了集装箱。

界、星号、总计与差距
--------------------

* **理论界**\ 一行给出每个 case 目前最好的界：背包族取最小的合法上界（有 CP-SAT 证明时取它，否则取 PackingSolver 自报的界），装箱族取最大的合法下界（体积界、PackingSolver 自报的界，以及 Martello-Pisinger-Vigo 类的构造性下界）。
* 数值后面的 ``*`` 表示等于该界，即该 case 的\ **已证明最优**。星号只给解同一问题变体的参与者；放松了约束的行拿不到星号。
* **总计**\ 是所有 case 的求和：背包族是利润（越大越好），装箱族是箱数（越小越好）。行按总计排序；有任何缺失或非法 case 的行排在最后。
* **理论界（差距）**\ 重复界的总计并给出到它的距离：利润用百分比，箱数用箱数差。``0`` 表示每个 case 都达到了界。

问题变体
--------

三个族里有两个固定每件物品的朝向。py3dbp、jerry800416/3D-bin-packing 与 gedex/bp3d 无法被要求保持朝向，它们自由旋转，因此在这两个族上解的是\ **放松**\ 后的问题。它们的行标注"放松旋转约束"，其数值可以合理地超过固定姿态的界，并且在那里永远拿不到星号。THPACK9 族对所有人都允许全部朝向，所以没有任何一行是放松的。U-Nesting 的各策略和参照程序都遵守固定姿态。

第三方库是怎么驱动的
--------------------

Python 和 Go 的贪心库是装载启发式，没有背包目标的概念。在背包族上，给它们单个容器和两种顺序的物品列表（大件优先与按文件顺序），保留较好的合法装法，利润为它们成功放入的物品之和。在装箱族上，给它们每件物品一个候选箱，然后统计实际使用的箱数。U-Nesting 的策略只暴露单容器 API，于是逐个装箱：每次调用接收上一个容器剩下的物品，每次调用有策略自己的时间预算。Martello-Pisinger-Vigo 程序以生成器默认的一般装箱参数运行，报告一个下界和一个上界；CP-SAT 参照是固定姿态背包的精确模型，其 ``OPTIMAL`` 状态就是理论界一行采用的证明。

注意事项
--------

* **衡量的是范围，不是工程质量。** py3dbp、它的 Go 与 fork 变体以及 U-Nesting 的贪心策略是为了用简单规则在毫秒内装满一个容器而设计的；PackingSolver 是花完整个预算的 anytime 优化求解器。表格衡量的只是各自在既定预算下、在这些实例上返回什么，不多不少。
* **实例小、无附加约束。** 没有使用重量、稳定性、堆叠或卸货约束；几个库支持这类约束而 PackingSolver 的 ``box`` 求解器不支持。
* **单次运行、单台机器。** 元启发式和上游的 anytime 搜索在多次运行之间会有波动；已证明最优的格子是稳定的，其他格子可能变动几个单位。
* **线程。** PackingSolver 在背包 case 上用了多个核心，其他库单核运行。在 30 件的第 9 类 replicate 和 31 个 THPACK9 实例上它的求解约一秒就带着证明结束，所以线程差异解释不了那里的差距；在更大的 case 上它和元启发式一样用满 10 s。
* **第三方数据随文档发布。** 第三方摆放数据在 ``tools/benchmarks/third_party.json``\ ，每条附库版本、算法标签和预算。它们由维护者使用各库的公开发行版或 commit、通过不属于本仓库的薄适配器生成；本仓库能复现的是对每个存储摆放的独立重新校验，以及由此导出的每一个数字。
