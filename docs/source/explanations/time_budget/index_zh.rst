时间预算是怎么估出来的
======================

:func:`~packingsolver3d.recommend_time_budget` 要回答一个求解器自己不回答的问题：等多久才值？``ANYTIME`` 模式下 PackingSolver 会一直跑到时限（:doc:`/explanations/upstream_behaviours/index_zh`），时限太短返回的是被截断的一轮，太长则浪费用户的时间。本页解释推荐值背后的模型、拟合用的数据和局限。采集脚本、拟合常数和完整表格在仓库的 ``experiments/time_budget/`` 目录。

每条算法路径一个公式
--------------------

上游按实例形状选算法：箱数、每箱平均件数（最大箱体积除以平均件体积）、每类平均份数，阈值是 16 和 64。:func:`~packingsolver3d.algorithm_path` 复刻了这一选择，并与 3140 次产出了解的记录运行的事件标签全部一致。模型于是是每条路径一个小公式，按算法各自的行为而非单纯按数据搭建：

.. math::

    T(\alpha) = L \,(1 + m(\alpha)) + c(\alpha)

* :math:`L` 是到首个解的**延迟**：完整跑一轮的代价。``TSMS``（最大空间树搜索，多件单箱 ``box`` knapsack）是块生成加第一遍束搜索；``SOR``（单箱 ``boxstacks``）是第一遍"序贯一维-矩形"；``SSK`` 与 ``SVC``（多箱）是对所有箱子的第一次迭代。它是实例规模（``box`` 用件数，``boxstacks`` 用立柱数）与品类数的幂律 :math:`L = e^{a}\, \mathrm{size}^{b}\, \mathrm{types}^{c}`，再加两个算法特有的项：``TSMS`` 在品类数达到四个及以上时加一个常数块生成步（块生成撞到 10000 块的上限后，代价与规模无关）；``SOR`` 在货物装不下箱子时乘一个常数（此时一维阶段必须做选择，这正是超载首轮慢的原因）。
* **增长型路径**（``TSMS``、``TS``、``SOR``）每轮把队列翻倍，到第 :math:`k` 轮的代价是 :math:`L\,(2^k - 1)`，所以首解之后值得再等的时间是 :math:`L` 的倍数 :math:`m(\alpha)`。**单轮型路径**（``SSK``、box 与 boxstacks 的 ``SVC``）在首个完整解之后基本就结束了——``SSK`` 通常能证明最优，``SVC`` 在两箱以内或全部装完时自行停止——所以 :math:`m = 0`，只剩一个很小的加法项 :math:`c(\alpha)`。

系数在对数空间做最小二乘拟合，并约束指数非负（更大或更杂的实例永远不会得到更短的预算），然后把截距抬到残差的覆盖分位：增长型路径 90%，单轮型路径 98%（运行会自行结束，慷慨的上限不花钱）。这就是推荐值是宽松上限而非中位数的原因。

``alpha`` 的含义
----------------

对每条记录的曲线 :math:`q(t)`（时刻 :math:`t` 的值相对 60 s 或 150 s 长跑终值）和每个候选预算 :math:`t`，分数

.. math::

    F_\alpha = \frac{(1 + \alpha^2)\, S\, q}{\alpha^2 S + q}, \qquad S = \frac{1}{1 + t / 60\,\mathrm{s}}

像 F-beta 组合召回与精确那样组合质量和以一分钟等待为尺度的速度分：:math:`\alpha \to \infty` 只看质量，:math:`\alpha \to 0` 只看速度。每条曲线的最大值点 :math:`T^*(\alpha)` 就是该实例应得的预算；:math:`m(\alpha)` 是该路径所有实例的 :math:`(T^* - L) / L` 的 80% 分位。因此 ``alpha`` 只通过 :math:`m` 与 :math:`c` 进入公式，在 0.25、0.5、1、1.5、2、3、4、6、8 上制表并按 :math:`\log\alpha` 插值。``alpha=4`` 是均衡默认值，``alpha=8`` 偏向质量。改动 :math:`S` 里的那一分钟与调 ``alpha`` 是同一根杠杆，所以固定不动。

停滞停止
--------

预算附带 ``stop_when_unimproved_after = max(L, T/2)``——前半段预算内不停，预期首解之前不停——以及 ``stop_when_unimproved_for = max(2\,\mathrm{s}, (T - L)/2)``：搜索沉默了改进窗口的一半就停。在记录的曲线上回放，``alpha=4`` 时 ``TSMS`` 的中位求解提前 20% 结束，``alpha=8`` 时提前 20–45%，落在参考值 1% 以内的实例占比损失不到一个点；单轮型路径不受影响，因为它们本来就自行结束。

数据
----

3158 次 ``ANYTIME`` 求解，每个实例一次，记录 :doc:`进度事件 </how_to/budgets/index_zh>`：上游 ``box`` knapsack 族 bischoff1995（700）、davies1999（900）、egeblad2009（60）、loh1992（15），ivancic1989 作多箱 bin packing（47），ROADEF 2022 单车 ``boxstacks`` 实例分层抽样 1240 个，160 个合成集装箱货载（20 尺与 40 尺柜、2 到 40 个品类、0.6 到 2.0 倍柜容的货、knapsack 与 bin packing、两种求解器），以及 40 尺示例柜的三种变体各三次重复。参考长跑为 60 s（上游族）或 150 s（集装箱货载）。ROADEF 实例很小（件数中位 41），远在一秒内结束；它们参与评估但不参与拟合，以免淹没 ``boxstacks`` 的路径。计时在一台 16 核机器上以 13 路并行测得，再用其中 80 个实例的空闲机复跑校准；参考机器与上游 commit 记在 ``packingsolver3d._time_budget_constants.REFERENCE``。

局限
----

* 模型知道算法，不知道几何。规模、品类数、装载比都相同的两个实例，延迟可以差好几倍（各路径对数残差的标准差在 0.4 到 1.1 之间）；覆盖分位靠高估来吸收这一点。
* 多箱的 ``boxstacks`` 在所钉住的 commit 上天生慢：``SVC`` 用完整的定长队列跑完每一个箱子才报任何解，40 个合成 bin packing 货载中有 17 个在 150 s 内无解。这条路径的推荐值就是 98% 分位的延迟、封顶 600 s；推荐值撞到封顶时应理解为"这种实例形状超出了多箱 ``boxstacks`` 路径能快速处理的范围"。
* 很小的实例（几十件上的 ``TS``）得到几秒的常数：它们的首解是瞬时的，之后每多一秒只换来千分之几。
* ``alpha=8`` 会有意在超载的集装箱上花几分钟，因为它们的曲线确实持续改进好几分钟；交互式工具嫌长的话，用 ``alpha=4`` 加停滞停止。
