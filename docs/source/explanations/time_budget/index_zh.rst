时间预算是怎么估出来的
======================

:func:`~packingsolver3d.recommend_time_budget` 要回答一个求解器自己不回答的问题：等多久才值？``ANYTIME`` 模式下 PackingSolver 会一直跑到时限（:doc:`/explanations/upstream_behaviours/index_zh`），时限太短返回的是被截断的一轮，太长则浪费用户的时间。本页解释推荐值背后的模型、拟合用的数据和局限。采集脚本、拟合常数和完整表格在仓库的 ``experiments/time_budget/`` 目录。

每条算法路径一个公式
--------------------

上游按实例形状选算法：箱数、每箱平均件数（最大箱体积除以平均件体积）、每类平均份数，阈值是 16 和 64。:func:`~packingsolver3d.algorithm_path` 复刻了这一选择，并与 3140 次产出了解的记录运行的事件标签全部一致。模型于是是每条路径一个小公式，按算法各自的行为而非单纯按数据搭建：

.. math::

    T(\alpha) = L \,(1 + m(\alpha)) + c(\alpha)

* :math:`L` 是到首个解的**延迟**：完整跑一轮的代价。``TSMS``（最大空间树搜索，多件单箱 ``box`` knapsack）是块生成加第一遍束搜索；``SOR``（单箱 ``boxstacks``）是第一遍"序贯一维-矩形"；``SSK`` 与 ``SVC``（多箱）是对所有箱子的第一次迭代。它是实例规模（``box`` 用件数，``boxstacks`` 用立柱数）与品类数的幂律 :math:`L = e^{a}\, \mathrm{size}^{b}\, \mathrm{types}^{c}`，再加两个算法特有的项：``TSMS`` 在品类数达到四个及以上时加一个常数块生成步（块生成撞到 10000 块的上限后，代价与规模无关）；``SOR`` 在货物装不下箱子时乘一个常数（此时一维阶段必须做选择，这正是超载首轮慢的原因）。
* **增长型路径**\ （``TSMS``、``TS``、``SOR``）每轮把队列翻倍，到第 :math:`k` 轮的代价是 :math:`L\,(2^k - 1)`，所以首解之后值得再等的时间是 :math:`L` 的倍数 :math:`m(\alpha)`。**单轮型路径**\ （``SSK``、box 与 boxstacks 的 ``SVC``）在首个完整解之后基本就结束了——``SSK`` 通常能证明最优，``SVC`` 在两箱以内或全部装完时自行停止——所以 :math:`m = 0`，只剩一个很小的加法项 :math:`c(\alpha)`。

系数在对数空间做最小二乘拟合，并约束指数非负（更大或更杂的实例永远不会得到更短的预算），然后把截距抬到残差的覆盖分位：增长型路径 90%，单轮型路径 98%（运行会自行结束，慷慨的上限不花钱）。这就是推荐值是宽松上限而非中位数的原因。

``alpha`` 的含义
----------------

对每条记录的曲线 :math:`q(t)`（时刻 :math:`t` 的值相对 60 s 或 150 s 长跑终值）和每个候选预算 :math:`t`，分数

.. math::

    F_\alpha = \frac{(1 + \alpha^2)\, S\, q}{\alpha^2 S + q}, \qquad S = \frac{1}{1 + t / 60\,\mathrm{s}}

像 F-beta 组合召回与精确那样组合质量和以一分钟等待为尺度的速度分：:math:`\alpha \to \infty` 只看质量，:math:`\alpha \to 0` 只看速度。每条曲线的最大值点 :math:`T^*(\alpha)` 就是该实例应得的预算；:math:`m(\alpha)` 是该路径所有实例的 :math:`(T^* - L) / L` 的 80% 分位。因此 ``alpha`` 只通过 :math:`m` 与 :math:`c` 进入公式，在 0.25、0.5、1、1.5、2、3、4、6、8 上制表并按 :math:`\log\alpha` 插值。``alpha=4`` 均衡，是 ``box`` 的默认值；``alpha=8`` 偏向质量，是 ``boxstacks`` 的默认值（``DEFAULT_ALPHA``）：在本次实验的集装箱货载上，``alpha=4`` 让 16% 的单箱 ``boxstacks`` 求解停在参考值 99% 以下，``alpha=8`` 一个都没有，代价是多等约一分钟。改动 :math:`S` 里的那一分钟与调 ``alpha`` 是同一根杠杆，所以固定不动。

停滞停止
--------

预算附带的是*相对*停滞停止：``stop_when_unimproved_after = L``（不早于覆盖分位的首解延迟；给了倍数后看门狗也绝不在真正的首个解出现前触发）、``stop_when_unimproved_for = 5 s`` 作下限、``stop_when_unimproved_ratio = alpha / 2`` 夹在 1 到 4 之间——搜索沉默的时长达到上次改进时刻的这么多倍就停。这个形状来自算法本身：增长型路径各轮在约 :math:`L, 3L, 7L, 15L, \dots` 结束，等下一轮的代价等于至今已花的时间；倍数 1.14 能看到再一轮结束，3.4 能看到两轮。固定耐心做不到这一点：小了会把每个后期的轮次砍断，大了则浪费大半预算。0.0.3 正因此发布了 ``after = max(L, T/2)``、``patience = (T − L)/2``，结果求解通常在时限的 0.5 到 0.85 处结束，停滞停止几乎失去意义。在记录的曲线上回放（空闲机秒；T 为时限）：

停止策略对比
------------

预算是一套*策略*而不只是一个数：时限、最早可停时刻、耐心。三种停法在全部记录曲线上回放（``experiments/time_budget/policy_compare.py``），并模拟机器比假设慢 2 倍 / 快 2 倍而策略参数（以秒计）不变的情形：

* **A，只用时限**——公式给的 ``time_limit``，别的都不用。
* **B，只用停滞停止**——从求解开始计时、固定耐心 3 / 5 / 10 s，上限 600 s；**B_L** 同 B，但预测首解 :math:`L` 之前不停。
* **C，0.0.3 发布的组合**——``time_limit`` 作上限，``after = max(L, T/2)``，``patience = max(2 s, (T − L)/2)``。

回放说明了什么：

* 单靠停滞停止替代不了预算。它在 ``TSMS``（一两秒出首解）上对机器速度最不敏感，但在所有首解慢的路径上会在拿到任何解之前就停：单箱 ``boxstacks`` 货载 20–45%、多箱 ``box`` 货载 25–36%、多箱 ``boxstacks`` 货载 78–100% 以无解收场。最早可停时刻的守门需要延迟模型，这正是 ``stop_when_unimproved_after`` 存在、并由 :math:`L` 填值的原因。
* 固定耐心还会和算法本身打架：队列翻倍的路径让改进之间的间隔越来越长，常数耐心总会在某一级把搜索砍断，损失就是后面几级本可再涨的部分（10 s 耐心下 20–27% 的 ``SOR`` 货载停在 99% 以下）。耐心必须随改进窗口缩放，``(T − L)/2`` 做的就是这件事。
* 单靠时限可预测（它就是进度条刻度）、在模型准的地方也准，但机器比假设慢就会截断（``TSMS`` 从 4.5% 变 13.9% 低于 99%），机器快则浪费（快 2 倍的机器上 ``alpha=8`` 有一半求解一直跑到时限）。
* 组合 C 在速度估对时以同等质量用时最短，在快机器上会自行提前结束。弱点是 ``after`` 与 ``patience`` 都是绝对秒数：机器慢 2 倍时 ``alpha=4`` 有 4.4% 的 ``TSMS`` 求解停在首解之前；``alpha=8`` 对这一误差的容忍度好得多，校准 ``speed`` 则可消除它。
* 按*实测*改进时刻的倍数给耐心，就是 C 的抗速度误差版本：D 把它做进了看门狗本身（``stop_when_unimproved_ratio``），调用方不再需要用回调实现第二触发。

给调用方的设计参考
------------------

:class:`~packingsolver3d.TimeBudget` 各字段的用途，面向 Stowly 这类桌面工具写：它的设置里有一个"最长时间"，自停滞停止存在以来还有一个"N 秒无改进即停"。

* ``time_limit`` 就是*最长时间*设置，也是按时间推进的进度条的满刻度。求解通常会在它之前结束：它是覆盖分位，不是中位数。
* ``stop_when_unimproved_for``、``stop_when_unimproved_after`` 与 ``stop_when_unimproved_ratio`` 就是*停滞即停*设置；三个都从预算填，而不是让用户填一个数，因为第二个守护首解慢的路径，倍数让耐心跟着算法走（显示成"距上次改进 *倍数* 倍时长无新改进即停，至少 *下限* 秒"）。``RunRecord.stop_reason`` 为 ``'unimproved'`` 是正常且好的结果，值得显示为"提前结束：N 秒无改进"。
* ``alpha`` 是唯一值得暴露的旋钮，做成粗档位（更快 / 均衡 / 更充分 对应 2 / 4 / 8）而不是数字；保留按求解器的默认值（``box`` 4，``boxstacks`` 8）。
* ``speed`` 应该校准而不是手填：每次求解后用第一个 :class:`~packingsolver3d.ProgressEvent` 算 ``budget.typical_latency * budget.speed / 实测首解时间``（用中位预测，不用覆盖分位的 ``latency``），跨次指数平滑（最新值权重 0.3 左右即可），按机器持久化。尚无校准时优先用 ``alpha=8`` 或小于 1 的 ``speed``：回放显示组合策略在机器比假设快时退化温和，比假设慢时退化剧烈。
* ``path``、``latency``、``improvement`` 用来解释："预计约 L 秒出首解"，以及在 ``boxstacks`` 多箱 knapsack / 变尺寸装箱（``path == 'SVC'``）或 ``time_limit`` 撞到 600 s 封顶时给出提示，因为这些形状正是所钉住的上游处理得慢的。
* 不再需要第二触发：相对耐心已内建在看门狗里。返回 ``False`` 的 ``progress_callback`` 仍可用于用户自己的停止按钮。

数据
----

3158 次 ``ANYTIME`` 求解，每个实例一次，记录 :doc:`进度事件 </how_to/budgets/index_zh>`：上游 ``box`` knapsack 族 bischoff1995（700）、davies1999（900）、egeblad2009（60）、loh1992（15），ivancic1989 作多箱 bin packing（47），ROADEF 2022 单车 ``boxstacks`` 实例分层抽样 1240 个，160 个合成集装箱货载（20 尺与 40 尺柜、2 到 40 个品类、0.6 到 2.0 倍柜容的货、knapsack 与 bin packing、两种求解器），以及 40 尺示例柜的三种变体各三次重复。参考长跑为 60 s（上游族）或 150 s（集装箱货载）。ROADEF 实例很小（件数中位 41），远在一秒内结束；它们参与评估但不参与拟合，以免淹没 ``boxstacks`` 的路径。计时在一台 16 核机器上以 13 路并行测得，再用其中 80 个实例的空闲机复跑校准；参考机器与上游 commit 记在 ``packingsolver3d._time_budget_constants.REFERENCE``。上游 ``9bfb9431`` 改变多箱 ``boxstacks`` 路径后，所有非 ROADEF 的 ``boxstacks`` 运行在 ``d10db9d7`` 上重测（122 次，同样的时限与并发条件，另加 24 个多箱 knapsack 货载用于拟合 ``SVC`` 路径）；``box`` 路径与 ROADEF 抽样沿用 ``2a598481`` 的测量。

局限
----

* 模型知道算法，不知道几何。规模、品类数、装载比都相同的两个实例，延迟可以差好几倍（各路径对数残差的标准差在 0.4 到 1.1 之间）；覆盖分位靠高估来吸收这一点。
* 多箱的 ``boxstacks`` 有两种速度。bin packing 走 ``SSK``（上游 ``9bfb9431`` 起），在集装箱货载上一秒内报解，但 49 个 bin packing 货载中有 14 个在 150 s 内无解：贪心一轮装不下，而此前每个上游版本也都装不下，多半是箱数本身不可行。knapsack 与变尺寸装箱仍走 ``SVC``，多箱 knapsack 货载上首个完整解中位 40 秒；这条路径的推荐值就是 98% 分位的延迟、封顶 600 s；推荐值撞到封顶时应理解为"这种实例形状超出了多箱 ``boxstacks`` 路径能快速处理的范围"。
* 很小的实例（几十件上的 ``TS``）得到几秒的常数：它们的首解是瞬时的，之后每多一秒只换来千分之几。
* ``alpha=8`` 会有意在超载的集装箱上花几分钟，因为它们的曲线确实持续改进好几分钟；交互式工具嫌长的话，``box`` 用 ``alpha=4``（默认）、``boxstacks`` 用 ``alpha=6``，并保留停滞停止。
